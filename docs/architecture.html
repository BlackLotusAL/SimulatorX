01

ARCHITECTURE

谁负责哪一段工作

整机负责“把设备准备好”，宿主负责“让服务可靠运行”，设备模型负责“像设备一样作出反应”。SUT 是使用这些设备的业务系统，位于框架之外。

复用到基础设施为止

每个独立设备维护自己的行为、业务常量、节点资源、报文与 ABI 映射。行为相同或仅参数不同，也采用独立设备包；可以复制起步，之后分别维护。共享的只是整机环境、协议宿主和运行通信机制。

SimulatorX 配置和控制在父进程；每个硬件独立启动服务进程

运行时能装配，不等于源码直接依赖

源码 import 方向

入口 → framework
protocols → framework
设备实现 → protocols 的契约

公共层没有 import 真空、旋转轴或参考 TCP 包。

配置加载方向

type ⇢ 内置协议硬件句柄
子系统 ID／硬件 ID ⇢ 设备包
model.py:create ⇢ 设备定义
设备定义 ⇢ 模型与协议适配器

三协议统一加载 ID 对应设备包的 model.py:create。装配工厂不启动资源。

统一启动与回收

框架启动独立进程，分配端口／socket，退出时关闭客户端和进程。每个实例独立状态，不设置运行模式。

三协议固定约定

子系统 ID／硬件 ID 对应 src/subsystems 下设备目录；model.py:create 是统一入口。PLC 映射固定在 resources/bindings.json，XML 文件名由 nodeset 指定。

共享通信与运行模块

源码依赖方向

transport → runner → pipe → messages

transport 还直接依赖 messages；runner 不反向依赖 socket 传输。原有 transport 公共符号仍可导入。

四个职责边界

transport 管理 socket 消息与监听器；runner 启动服务、报告就绪并监测退出；pipe 串行处理父子进程请求；messages 定义消息大小、数值规则、诊断转换和环境错误。

失败也是流程的一部分

预检失败：不启动任何服务。启动失败：包含失败硬件在内逆序清理。Reset 失败：整机标记 failed，禁止继续复用。退出时释放客户端并停止所有已创建服务。

--simulatorx-artifacts 保存仿真诊断，默认 artifacts/simulatorx；--sut-artifacts 保存 SUT 诊断，示例默认 artifacts/sut。

CLI 的显式 --ready-file 输出由调用方保留；JUnit XML 由 pytest 的报告参数产生，不是服务自动写入的数据库。

一个清单完成整机装配

现有 src/device.json 决定运行哪些硬件，所有硬件设置直接内联；三协议入口固定为各包 model.py:create，不再维护硬件配置文件。无需另建 device.local.json；该名称没有特殊含义。临时运行子集可用 --select，不引入多环境继承或配置覆盖。

ID 与资源路径约定

子系统和硬件 ID 必须是合法的非关键字 Python 包名，对应 src/subsystems/子系统/硬件。nodeset 相对该包 resources 目录解析，也支持绝对 XML 路径；映射固定为 resources/bindings.json。清单位置和当前工作目录不改变设备定位。CLI 显式路径仍相对工作目录。

新增独立腔室怎么做

  1. 复制现有腔室包到新包，例如 subsystems.vacuum.load_lock_plc，作为独立开发起点。
  2. 修改本包 model.py 的 PARAMETERS 与业务规则；独立维护节点、对象、Reset 标识和 bindings。
  3. model.py 的 create() 声明行为和协议标识；整机清单硬件条目直接填写与目录相同的 ID、type、nodeset 和端口。
  4. 补齐本设备行为、节点、Reset 和 SUT 验收，不导入、继承或委托旧设备业务。

PLC 主要维护 model.py、XML 和 bindings.json，设备子目录无需 __init__.py，仅 subsystems 顶层保留；不再要求独立 definition.py 或 bindings.py。bindings.json 人工维护业务名称、类型与 Reset 基线，fixture SetUp 通过映射定位并写入节点；不引入自动生成流程。该新包只是说明示例，本轮不新增第二个生产腔室。测试使用两个运行对象加载同一设备包验证隔离，不支持硬件 ID 别名，这不是生产设备共享业务的开发方式。

旧配置需要迁移

旧 mode、连接已有服务的字段、config/definition/package 入口覆盖、PLC bindings 覆盖，以及 profile、parameters、protocol 均在预检拒绝。业务常量在独立设备包中维护。业务命令中的运动目标与速度，以及测试故障／序列注入继续有效。

测试分层与运行入口

根套件位于 src/test：framework 验证配置、依赖边界和运行机制，protocols 验证共享宿主，subsystems 验证独立设备，integration 验证 CLI 与整机运行时。外部 SUT 验收位于 examples/sut_integration，需单独运行。

integration 按实际资源依赖标记真实服务、socket、子进程或原生构建，不按目录名判断；linux_sdk 标识需要 Linux 和 C 编译器的用例。默认完整执行；快速筛选不会替代完整三协议验收。共享 device fixture 要求串行执行，拒绝 pytest-xdist 多 worker。

术语，用一句话解释

宿主
承载模型的服务外壳：帮设备处理连接、线程、健康检查和诊断。
SUT
被测业务系统。它发出业务动作并判断设备反馈，SimulatorX 只提供可控环境。
ABI
原生库与调用程序约定的函数名、参数、返回值和内存布局，必须严格匹配。
RPC
把“调用操作＋参数”发给另一个进程并等待结果；这里主要用于本地测试控制。
Reset
恢复当前实例的基线状态，通常不重启进程；失败后不能继续复用环境。
业务通道
SUT 实际使用的 OPC UA 接口、SDK 二进制 socket 或 TCP 业务报文连接。
控制通道
测试用来设条件、读诊断和 Reset 的接口：PLC 使用原生节点与方法，SDK 使用独立控制 socket，TCP 使用父子进程 stdin/stdout 管道，不增加控制监听端口。
