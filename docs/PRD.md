## 1. 文档目的

本文档定义 SimulatorX 首个版本的产品目标、范围、核心能力、对外契约、非功能指标与验收标准。本文档是后续架构设计、开发拆分和测试验收的需求基线，不规定具体 Python 库、进程模型或内部目录结构。

## 2. 背景与问题

系统级自动化测试需要依赖 OPC UA PLC 节点及基于 TCP Socket 的本地设备。直接使用真实设备会受到设备数量、部署成本、状态复现、异常制造和流水线并发等限制，难以形成稳定、可重复的自动化测试环境。

现有需求还面临以下问题：

- 仿真程序和测试用例会频繁由 Coding Agent 扩展，如果缺少稳定边界，Agent 容易修改框架核心并引入回归。
- 流水线需要在测试 Setup 中设置异常数据，并在 Teardown 中可靠恢复；测试失败或流水线取消也不能污染后续用例。
- 同一服务器上的不同账号可能同时运行仿真，分散或写死的端口容易冲突。
- 一套系统级环境包含多个彼此独立的子系统，需要统一启停、查询和清理，同时保持状态、日志和异常作用域隔离。
- 真空度、运动轴位置等数据既需要简单的静态异常覆盖，也需要由可重复的物理模型产生更接近真实设备的变化过程。

SimulatorX 将上述能力收敛为一个本地、自动化优先、可扩展的 Python 仿真框架。

## 3. 产品目标与成功标准

### 3.1 产品目标

1. **Agent 友好**：Coding Agent 能依照 Schema、模板、示例和插件契约新增子系统、协议、模型与测试，不修改框架核心。
2. **测试友好**：pytest 和通用流水线能够稳定完成启动、复位、异常应用、异常清除和停止，并正确处理失败路径。
3. **协议覆盖**：以 Server 角色仿真 OPC UA PLC 节点和基于 TCP 的自定义报文设备。
4. **数据异常仿真**：支持直接覆盖输出数据，也支持扰动物理模型输入或参数，验证 SUT 的流程中断、报警和提示行为。
5. **并发隔离**：同一主机不同账号可并行运行，端口、进程、状态、日志和清理操作互不干扰。
6. **统一生命周期**：通过跨平台 Python CLI/脚本一键启动和停止整套环境，并提供状态、复位和残留清理能力。
7. **可重复性**：相同配置、基线和随机种子得到可重复的模型及异常结果。

### 3.2 首版成功标准

- 新增一种子系统配置、TCP 协议插件、物理模型或 pytest 测试时，无需修改框架核心，且可独立完成 Schema/契约校验。
- 在 Linux 和 Windows 上完成同等的启动、状态查询、复位、异常控制、停止和清理流程。
- 不同操作系统账号并发运行时不发生端口占用冲突，也不会互相停止或清理对方环境。
- 测试失败、Setup 失败、部分启动失败或流水线取消后，不遗留占用端口的仿真进程或未清除的异常状态。
- 在约定参考主机和容量下满足启动、复位和停止时延指标。

## 4. 用户角色

### 4.1 仿真开发者与 Coding Agent

- 根据模板创建子系统定义、TCP 编解码插件和物理模型。
- 使用机器可读 Schema 与契约测试在提交前发现配置或接口错误。
- 只通过扩展点增加能力，不理解或修改框架内部编排代码。

### 4.2 自动化测试开发者

- 在 pytest 或其他流水线中启动或复用环境。
- 在用例 Setup 中复位基线并应用异常场景。
- 验证 SUT 对异常真空度、异常轴位置、状态码或质量码的反应。
- 在 Teardown 中清除异常；即使用例断言失败也不污染下一条用例。

### 4.3 流水线维护与排障人员

- 查询环境是否就绪、实际端点、组件状态和当前异常。
- 区分配置错误、仿真基础设施错误和 SUT 业务失败。
- 在任务被取消或异常中断后确认自动回收结果，并按账号所有权清理残留。

## 5. 产品范围

### 5.1 首版范围

- Linux 与 Windows 本地运行。
- 每个操作系统账号同一时刻一套活动环境。
- 每套环境最多 20 个相互独立的子系统。
- OPC UA Server 仿真。
- TCP 自定义协议 Server 仿真和多协议插件扩展。
- 版本化 YAML 配置、机器可读 Schema、模板和示例。
- Python CLI、Python SDK 与 pytest 一等集成。
- 统一端口配置、动态端口发现和 endpoint manifest。
- 任务级环境复用、用例级原地复位和异常清理。
- 静态数据覆盖、模型输入/参数扰动及软实时模型运行。
- 真空模型和单轴运动模型的实用参考实现要求。
- 结构化日志、诊断产物、异常退出自动回收和手工清理。

### 5.2 非目标

首版明确不包含：

- Web 或桌面 GUI。
- 跨主机部署与集中编排。
- 同一账号同时运行多套环境。
- 跨子系统联动。
- 同一子系统内 OPC UA 与 TCP 端点的状态或模型联动。
- 标准 Modbus TCP 兼容性。
- 断连、拒绝连接、延迟、超时、丢包、截断、乱序、畸形包等通信层故障注入。
- CPU、内存、磁盘、网络带宽等主机资源故障注入。
- 硬实时调度或毫秒级确定性时限保证。
- 生产级标定的多腔体真空系统、多轴插补或联动控制模型。
- OPC UA 方法、事件及生产级证书、用户认证和安全策略。
- 连接或控制真实生产设备。

## 6. 核心概念与约束

| 概念 | 定义 |
| --- | --- |
| 环境（Environment） | 当前账号统一启动、复位、停止和清理的一套仿真集合。每个账号最多有一套活动环境。 |
| 子系统（Subsystem） | 环境内的逻辑分组。子系统之间不存在状态共享、异常传播或生命周期联动逻辑。 |
| 端点（Endpoint） | 一个 OPC UA Server 或 TCP Server。即使属于同一子系统，不同端点也拥有独立状态、模型和异常作用域。 |
| 基线（Baseline） | 测试开始前端点数据、模型参数、计数器和随机种子的确定性初始状态。 |
| 模型（Model） | 按软实时步进更新端点私有状态的 Python 插件。模型不跨端点共享状态。 |
| 异常场景（Scenario） | 对指定端点、节点、信号或模型参数施加的数据/业务状态异常，可应用、查询和清除。 |
| Endpoint Manifest | 环境就绪后生成的 JSON 文件，记录 SUT 实际应连接的端点、端口和运行元数据。 |
| 运行产物（Artifacts） | 配置快照、manifest、状态快照、模型/异常事件和结构化日志等 CI 可归档文件。 |

### 6.1 隔离原则

- 环境、子系统和端点均须使用稳定且唯一的 ID。
- 不同账号的运行目录、进程信息、端口记录和日志必须隔离。
- 所有停止与清理操作必须验证账号所有权，不得通过模糊进程名批量终止。
- 对某个端点应用异常时，不得改变其他端点或子系统的状态、时钟、随机序列或输出。

### 6.2 配置与扩展原则

- 常规节点、初始值、端口策略、插件引用、模型参数和异常场景使用声明式 YAML。
- 自定义协议编解码、复杂状态机和数值模型使用稳定的 Python 插件接口。
- 配置 Schema 和插件接口必须显式版本化；不兼容变更只能通过新的主版本发布。
- 配置错误必须在启动任何服务前尽可能一次性报告，并给出字段路径、期望值和修复提示。

## 7. 关键用户流程

### 7.1 仿真开发流程

1. 从模板创建子系统配置、端点、协议或模型插件。
2. 填写稳定 ID、能力声明、配置 Schema 和默认基线。
3. 运行静态配置校验和插件契约校验。
4. 使用最小示例独立启动新增端点。
5. 新增 pytest 场景，验证正常数据、异常数据和复位行为。
6. 整个过程不修改框架核心。

### 7.2 流水线默认流程

1. 流水线读取环境配置并执行校验。
2. 创建当前账号的受监管环境，动态分配端口并启动全部端点。
3. 等待所有端点真正就绪，随后生成 endpoint manifest。
4. 启动或配置 SUT，使其读取 manifest 中的实际端点。
5. 每条测试前执行原地 Reset，恢复确定性基线。
6. 在 Setup 中应用静态输出覆盖或模型扰动场景。
7. 执行测试并观察 SUT 的流程、报警或提示行为。
8. 在 Teardown 中清除当前用例的异常并再次恢复基线。
9. 测试任务结束后停止环境并归档诊断产物。

### 7.3 异常退出流程

- Setup、测试断言或 Teardown 失败时，框架仍须执行当前用例作用域的异常清除。
- 任一端点启动失败时，Start 失败并回滚已启动端点，不发布 READY manifest。
- 流水线取消或控制进程异常退出时，受监管生命周期自动终止当前账号的子进程并释放端口。
- 若自动回收未完成，维护人员可执行幂等 Cleanup；Cleanup 只处理当前账号拥有且可验证的残留。

## 8. 功能需求

### 8.1 配置、Schema 与模板

| 编号 | 需求 |
| --- | --- |
| FR-CFG-01 | 使用 YAML 统一描述环境、子系统、端点、端口、节点、插件、模型、基线、随机种子和异常场景。 |
| FR-CFG-02 | 每份配置包含 `schema_version`，并可在不启动环境的情况下独立校验。 |
| FR-CFG-03 | 提供机器可读 Schema，以及子系统、TCP 协议、模型和 pytest 用例模板。 |
| FR-CFG-04 | 校验错误包含稳定错误码、字段路径、问题说明和修复建议。 |
| FR-CFG-05 | 所有端口只在统一环境配置中声明，不允许插件使用未登记的写死端口。 |
| FR-CFG-06 | 配置快照及其摘要必须写入运行产物，以便 CI 复现。 |

概念配置结构如下，字段名称用于约束产品契约，具体 Schema 在技术设计阶段细化：

```yaml
schema_version: "1"
environment:
  id: equipment-system
  random_seed: 20260821
  subsystems:
    - id: vacuum-subsystem
      endpoints:
        - id: vacuum-plc
          kind: opcua
          port: auto
          nodes: []
          model:
            plugin: reference.vacuum
            parameters: {}
          baseline: {}
          scenarios: []
        - id: vacuum-controller
          kind: tcp
          port: auto
          protocol_plugin: project.vacuum_protocol
          baseline: {}
          scenarios: []
```

### 8.2 Coding Agent 扩展契约

| 编号 | 需求 |
| --- | --- |
| FR-EXT-01 | 新增子系统只能增加配置、插件和对应测试，不得要求修改框架核心分支或注册表代码。 |
| FR-EXT-02 | TCP 协议插件必须通过统一契约声明配置、帧识别、解码、命令分发、响应编码和错误诊断能力。 |
| FR-EXT-03 | 模型插件必须通过统一契约声明参数、输入、输出、初始化、步进和 Reset 行为。 |
| FR-EXT-04 | 插件须可在不启动完整环境的情况下运行契约校验。 |
| FR-EXT-05 | 模板和示例须包含最小可运行实现、配置说明、预期产物及对应测试示例。 |
| FR-EXT-06 | 插件加载失败时不得留下监听端口或后台进程，错误必须定位到插件和配置路径。 |

### 8.3 环境生命周期

环境至少具有 `STOPPED`、`STARTING`、`READY`、`RESETTING`、`STOPPING` 和 `FAILED` 状态。

| 编号 | 需求 |
| --- | --- |
| FR-LIFE-01 | Start 在启动前完成配置、插件和账号活动环境检查。 |
| FR-LIFE-02 | 只有全部已配置端点完成监听、节点/协议加载和健康检查后，环境才进入 READY。 |
| FR-LIFE-03 | 部分启动失败必须回滚已启动资源，保留结构化失败诊断，但不得发布可供 SUT 使用的 READY manifest。 |
| FR-LIFE-04 | 同账号已有 READY 环境且配置摘要相同时，重复 Start 返回现有状态和 manifest；配置不同时明确拒绝，且不影响现有环境。 |
| FR-LIFE-05 | Stop、Reset、场景清除和 Cleanup 必须幂等；重复调用返回成功或明确的 already-stopped/already-clear 状态。 |
| FR-LIFE-06 | Stop 只终止当前账号环境，释放全部端口并完成日志刷新。 |
| FR-LIFE-07 | Status 提供环境、子系统、端点、实际端口、模型和活动场景的机器可读状态。 |
| FR-LIFE-08 | 受监管运行模式必须在流水线取消或控制进程退出时自动回收所属资源。 |

### 8.4 Reset 与测试隔离

| 编号 | 需求 |
| --- | --- |
| FR-RST-01 | 默认 Reset 原地执行，不改变监听地址、端口或 endpoint manifest。 |
| FR-RST-02 | Reset 清除所有活动异常，恢复基线数据、模型输入和参数、内部计数器及随机种子。 |
| FR-RST-03 | 相同配置和随机种子在 Reset 后必须产生相同的初始状态与随机序列。 |
| FR-RST-04 | 原地 Reset 失败时允许重启失败组件；如果无法恢复完整 READY 状态，整个 Reset 失败并返回明确诊断。 |
| FR-RST-05 | pytest 用例作用域必须保证即使 Setup 或测试失败，Teardown 仍尝试清除本用例异常。 |
| FR-RST-06 | 用例级异常不得泄漏到后续用例；测试基础设施应提供可验证的基线检查。 |

### 8.5 端口管理与账号隔离

| 编号 | 需求 |
| --- | --- |
| FR-PORT-01 | 每个 OPC UA/TCP 端点的端口配置支持 `auto` 或显式固定端口，默认使用 `auto`。 |
| FR-PORT-02 | 动态端口分配与实际监听从使用者视角必须是无竞争窗口的操作，跨账号并发启动不得分配重复端口。 |
| FR-PORT-03 | 固定端口已占用时快速失败，报告端点 ID 和冲突端口，并回滚本次启动产生的资源。 |
| FR-PORT-04 | READY 后生成 JSON endpoint manifest，作为 SUT 获取实际端点的唯一权威来源。 |
| FR-PORT-05 | manifest 至少包含 Schema 版本、环境 ID、账号所有者、配置摘要、状态、启动时间以及每个端点的协议、主机和端口。 |
| FR-PORT-06 | 不同账号的状态文件、manifest、PID/进程元数据和日志路径必须隔离。 |

Endpoint manifest 的概念结构如下：

```json
{
  "schema_version": "1",
  "environment_id": "equipment-system",
  "owner": "current-os-user",
  "state": "READY",
  "config_digest": "...",
  "started_at": "...",
  "endpoints": {
    "vacuum-subsystem.vacuum-plc": {
      "kind": "opcua",
      "host": "127.0.0.1",
      "port": 43125
    }
  },
  "artifacts": {
    "directory": "..."
  }
}
```

### 8.6 OPC UA Server 仿真

| 编号 | 需求 |
| --- | --- |
| FR-UA-01 | 首版只提供 OPC UA Server，由 SUT 作为 Client 主动连接。 |
| FR-UA-02 | 支持可配置的命名空间、节点层级和地址空间浏览。 |
| FR-UA-03 | 支持常见标量及数组数据类型、节点初始值、读写权限和可选写入处理逻辑。 |
| FR-UA-04 | 支持读取、写入、数据变更订阅、Source/Server 时间戳和质量码。 |
| FR-UA-05 | 节点写入可以更新该端点私有状态或模型输入，但不得影响其他端点。 |
| FR-UA-06 | 支持节点值越界、冻结、跳变、错误状态和 Bad 质量等数据异常。 |
| FR-UA-07 | 默认匿名、无加密，仅用于可信本地或 CI 网络。 |

### 8.7 TCP 自定义协议 Server 仿真

| 编号 | 需求 |
| --- | --- |
| FR-TCP-01 | 首版只提供 TCP Server，由 SUT 主动连接。 |
| FR-TCP-02 | 不同端点可加载不同 Python 协议插件，且插件状态不得跨端点共享。 |
| FR-TCP-03 | 框架统一提供连接接入、数据收发、插件调用、生命周期状态和结构化诊断。 |
| FR-TCP-04 | 协议插件负责帧边界识别、解码、业务命令映射、响应编码及协议级错误返回。 |
| FR-TCP-05 | 框架提供一个示例协议插件和对应契约测试；真实项目协议由使用项目根据自身规范实现。 |
| FR-TCP-06 | TCP 协议可以借鉴功能码、地址或寄存器等 Modbus 概念，但不声明标准 Modbus TCP 兼容。 |
| FR-TCP-07 | 首版异常只改变响应中的业务数据或状态，不改变连接、时序或报文完整性。 |
| FR-TCP-08 | 原始收发报文默认不落盘，可按端点或测试显式启用。 |

### 8.8 模型运行与参考模型

| 编号 | 需求 |
| --- | --- |
| FR-MOD-01 | 提供可配置步进周期的软实时模型调度能力，不承诺硬实时截止时间。 |
| FR-MOD-02 | 模型支持固定随机种子，并在 Reset 时恢复初始参数、状态和随机序列。 |
| FR-MOD-03 | 每个模型只服务其所属端点，不与同一子系统或其他子系统的模型共享可变状态。 |
| FR-MOD-04 | 真空参考模型支持抽气、放气、泄漏和目标压力变化曲线，并允许配置初始压力、目标压力和变化速率等参数。 |
| FR-MOD-05 | 单轴参考模型支持使能、回零、移动、停止、正负限位及速度/加速度约束，并输出位置、运动状态和报警状态。 |
| FR-MOD-06 | 参考模型用于验证框架能力，不宣称为经过真实设备参数标定的生产级数字孪生。 |

### 8.9 数据异常与场景控制

| 编号 | 需求 |
| --- | --- |
| FR-SCN-01 | 场景目标必须精确到环境内的子系统、端点及节点/信号/模型参数。 |
| FR-SCN-02 | 支持直接输出覆盖，包括固定异常值、越界、冻结、跳变、错误状态和 OPC UA Bad 质量。 |
| FR-SCN-03 | 支持模型扰动，包括修改模型输入或参数，使异常由模型继续演化并产生。 |
| FR-SCN-04 | 场景必须显式声明采用输出覆盖或模型扰动；框架不得静默混合两种作用层。 |
| FR-SCN-05 | 输出覆盖生效期间，对外值以覆盖结果为准；清除后恢复到当前模型值或基线定义值。 |
| FR-SCN-06 | 支持在 Setup 中应用静态异常，也支持测试执行过程中通过 SDK/CLI 应用或切换预定义场景。 |
| FR-SCN-07 | 应用场景只有在目标确认生效后才返回成功；目标不存在、参数非法或同目标场景冲突时，Setup 必须失败并给出机器可读原因。 |
| FR-SCN-08 | 每次场景应用生成唯一实例 ID，并记录环境、测试、目标、类型、参数、生效和清除时间。 |
| FR-SCN-09 | Clear 可按场景实例或当前用例作用域执行，且重复清除无副作用。 |

### 8.10 CLI、Python SDK 与 pytest

CLI 以安装后的 `simulatorx` 命令或等价的 `python -m simulatorx` 形式提供，所有启停入口均由 Python 实现。

| 命令 | 产品语义 |
| --- | --- |
| `validate` | 校验配置、Schema 和插件可加载性，不启动服务。 |
| `start` | 启动当前账号环境，等待 READY 并输出/写入 endpoint manifest。 |
| `status` | 查询环境、端点、模型、端口和活动场景；支持 JSON 输出。 |
| `reset` | 原地恢复确定性基线，必要时重启失败组件。 |
| `scenario apply` | 应用预定义异常场景，并返回场景实例 ID。 |
| `scenario clear` | 清除指定场景或当前测试作用域内的场景。 |
| `stop` | 幂等停止当前账号环境并释放资源。 |
| `cleanup` | 校验所有权后清理当前账号可验证的残留资源。 |

Python SDK 必须提供与上述命令等价的生命周期、状态和场景控制能力，且返回结构化对象或异常，不要求调用方解析控制台文本。

pytest 集成至少提供：

- 任务/会话作用域的环境 fixture：启动或附着当前环境，并在会话结束时停止。
- 函数作用域的用例 fixture：测试前 Reset，测试后清除异常并恢复基线。
- 场景 fixture 或上下文管理器：应用场景并在退出时自动清除。
- 用例独占模式：需要进程级隔离的测试可以单独启动和停止环境，但不是默认模式。

CLI 和 SDK 错误至少区分以下类别：配置非法、插件加载失败、环境已被不同配置占用、固定端口冲突、启动失败、环境未就绪、场景非法、所有权不匹配、Reset 失败和 Cleanup 失败。所有 CLI 命令必须使用稳定退出码，并支持机器可读 JSON 结果。

### 8.11 可观测性与诊断产物

| 编号 | 需求 |
| --- | --- |
| FR-OBS-01 | 结构化日志至少包含时间、级别、环境 ID、子系统 ID、端点 ID、事件类型和消息。 |
| FR-OBS-02 | 与测试相关的事件应关联 test case ID 和场景实例 ID。 |
| FR-OBS-03 | 默认产物包括配置快照、endpoint manifest、组件最终状态、模型/场景事件记录和结构化日志。 |
| FR-OBS-04 | 原始 TCP 报文记录为显式选项，默认关闭，避免不必要的磁盘占用和敏感数据暴露。 |
| FR-OBS-05 | 基础设施错误须标记所属阶段和组件，使 CI 能与 SUT 断言失败区分。 |
| FR-OBS-06 | 状态和诊断输出不得依赖读取其他账号的运行目录或进程信息。 |

## 9. 非功能需求

### 9.1 平台与语言

- 支持 Linux 和 Windows 的本地开发机及 CI Runner。
- Python 版本为 3.11 或更高。
- 框架运行逻辑、插件、启停和清理脚本全部使用 Python；YAML 与 JSON 仅作为配置和产物格式。
- 用户流程不得依赖只在单一操作系统可用的 Shell 脚本。

### 9.2 容量与性能

参考主机为 8 vCPU、16 GB 内存。在该主机上，一套环境的首版验收容量为：

- 最多 20 个子系统。
- 合计最多 10,000 个 OPC UA 节点。
- 合计最多 100 个并发 TCP 连接。

在上述规模和有效配置下：

- 全环境启动并进入 READY 不超过 30 秒。
- 原地 Reset 不超过 3 秒。
- Stop 完成并释放资源不超过 10 秒。

### 9.3 可靠性

- 生命周期和清理操作须可安全重试。
- Start 失败不得留下半启动环境。
- READY 表示所有公布端点可立即连接和使用，而非仅表示进程已创建。
- 受监管模式下，控制进程退出必须触发子进程和端口回收。

### 9.4 确定性

- 相同配置、基线、调用序列和随机种子应产生相同模型结果和异常行为。
- Reset 是测试隔离边界，不允许依赖上一个用例遗留状态。
- 时间相关模型使用统一框架时钟语义；系统时间不得直接成为不可控业务输入。

### 9.5 安全与所有权

- 默认只监听配置指定的本机地址；示例和默认配置使用回环地址。
- OPC UA 默认匿名、无加密，仅适用于可信测试网络。
- Cleanup 和 Stop 只能操作当前账号拥有且身份可验证的环境。
- 产品不得将其自身描述为真实设备控制或生产安全组件。

### 9.6 可维护性

- 公共配置、manifest、CLI、SDK 和插件契约必须版本化并有兼容性说明。
- 新扩展通过配置发现或标准插件发现机制加载，不新增框架核心条件分支。
- 面向 Agent 的模板、Schema、示例和错误信息必须与公共契约同步更新。

## 10. 验收场景

| 编号 | Given / When / Then |
| --- | --- |
| AC-01 | **Given** Linux 或 Windows 的全新测试环境，**When** 使用同一份有效配置执行 Start、Status、Reset 和 Stop，**Then** 全流程成功且无需平台专用 Shell 操作。 |
| AC-02 | **Given** 同一主机的两个账号，**When** 各自并发启动环境，**Then** 实际端口不重复，运行目录和日志不混用，停止账号 A 不影响账号 B。 |
| AC-03 | **Given** 多个端点配置为 `auto`，**When** 环境进入 READY，**Then** manifest 包含每个端点的实际地址，SUT 可据此立即连接。 |
| AC-04 | **Given** 一个固定端口已被占用，**When** Start，**Then** 在启动时限内明确报告冲突端点和端口，且不留下半启动资源。 |
| AC-05 | **Given** 同账号已有 READY 环境，**When** 使用相同配置再次 Start，**Then** 返回现有 manifest；使用不同配置 Start 时明确拒绝且不改变现有环境。 |
| AC-06 | **Given** 某端点启动失败，**When** 整体 Start，**Then** 已启动端点被回滚、不生成 READY manifest，并保留结构化诊断。 |
| AC-07 | **Given** 20 个子系统、10,000 个 OPC UA 节点和 100 个 TCP 连接的有效配置，**When** 执行生命周期操作，**Then** 满足 30 秒启动、3 秒 Reset 和 10 秒 Stop 指标。 |
| AC-08 | **Given** OPC UA 节点模型，**When** SUT 浏览、读写和订阅节点，**Then** 获得符合配置的数据类型、时间戳、质量码和变更通知。 |
| AC-09 | **Given** 一个按模板实现的 TCP 协议插件，**When** SUT 发送合法自定义报文，**Then** 插件正确解码、处理和编码响应，且无需修改框架核心。 |
| AC-10 | **Given** 真空度或轴位置的静态输出覆盖，**When** Setup 应用场景，**Then** 只有目标端点输出异常；Teardown 清除后恢复基线或模型当前值。 |
| AC-11 | **Given** 真空模型输入或单轴模型参数扰动，**When** 场景生效，**Then** 输出按模型演化并触发预期异常状态；清除和 Reset 后恢复确定性行为。 |
| AC-12 | **Given** 相同配置和随机种子，**When** 运行、Reset 并再次执行相同输入序列，**Then** 关键模型状态和输出序列一致。 |
| AC-13 | **Given** 同一子系统包含 OPC UA 与 TCP 端点，**When** 修改其中一个端点的值、模型或场景，**Then** 另一个端点的状态和输出不变。 |
| AC-14 | **Given** Setup 失败或测试断言抛出异常，**When** pytest 进入 Teardown，**Then** 当前用例异常被清除，下一条用例的基线检查通过。 |
| AC-15 | **Given** 流水线取消或控制进程异常退出，**When** 受监管生命周期执行回收，**Then** 当前账号的仿真进程终止且端口可再次使用，不影响其他账号。 |
| AC-16 | **Given** 已停止环境或已清除场景，**When** 重复执行 Stop、Clear、Reset 后 Cleanup，**Then** 操作安全幂等且不影响其他环境。 |
| AC-17 | **Given** Coding Agent 仅获得公共 Schema、模板和示例，**When** 新增子系统、协议插件、模型和 pytest 用例，**Then** 不修改框架核心即可通过独立校验并运行。 |
| AC-18 | **Given** 一次 CI 失败，**When** 排障人员读取归档产物，**Then** 能还原配置摘要、实际端点、组件最终状态、异常生效/清除事件，并判断失败属于配置、仿真基础设施还是 SUT。 |

## 11. 假设与外部依赖

- SUT 能在自身启动或连接仿真前读取 endpoint manifest，并接受动态端口注入。
- 运行环境允许当前账号监听本机 TCP 端口和管理自己启动的子进程。
- 真实 TCP 自定义报文规范由各使用项目提供，并通过协议插件接入。
- 生产级真空或运动模型的公式、标定参数和设备验收数据由使用项目提供。
- 仿真运行在可信本地或 CI 网络，不承担生产网络的身份认证和加密职责。
- 子系统及端点彼此独立；未来若需要联动，应作为新的产品能力单独设计，而不是通过共享全局可变状态实现。

## 12. 需求变更原则

以下变化会改变首版产品边界，必须更新 PRD 并重新评审：

- 要求同一账号并行运行多套环境或跨主机编排。
- 要求 OPC UA/TCP 端点或不同子系统共享状态并联动。
- 引入通信层、网络层或主机资源层故障注入。
- 要求标准 Modbus 兼容、OPC UA 生产级安全或硬实时保证。
- 容量、参考硬件或生命周期时延目标发生变化。
- SUT 无法消费动态 endpoint manifest，需要改为集中预分配固定端口。
